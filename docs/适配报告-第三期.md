## 1. 适配原则确认

本报告为第三期适配工作记录，承接前两期成果，围绕**用户提出的三条业务规则**与**部署文档可复现性审计**展开。

**核心适配规则（延续前两期）：**

1. **需求基准不变** — 原始设计文档中的业务功能、业务规则、用户角色、核心流程一律不修改
2. **代码优先适配** — 代码与需求不符时，优先修改代码适配需求，不反向修改需求
3. **一一对应原则** — 文档与代码、数据库一一对应，变更必须同步更新
4. **部署文档必须可操作** — 每一条部署步骤必须可在新机器上从零复现

**第三期新增适配原则：**

5. **文档即真值** — 部署文档声称的接口、端口、表数量、脚本行为必须以实际代码与实测为准；文档与实际不符时，优先修代码或文档使二者一致
6. **新增功能先审查后测试** — 本期所有改动均遵循"审查 → 测试 → 通过后交付"，每条修复附实测验证
7. **历史快照不改写** — 前两期报告及规划类文档中的历史结论（如"25 张表"）作为当时记录保留，现状以最新代码与文档为准

## 4. 部署文档审计与修复清单

### 4.1 审计结论

对 docs/deployment 全部 10 篇文档 + scripts/README.md + 关键脚本（windows/linux 的 config、00-check-env、05-start-backend）逐条对照代码与实测，发现：

| 类别 | 数量 | 概述 |
|------|------|------|
| 错误 | 6 类 | 接口不存在 / .env 缺失 / 端口矛盾 / 脚本变量未定义 / 日志说法不符 / 检查计数失真 |
| 缺失 | 5 类 | 表数量过时 / 缺 7 张表说明 / 前端配置文档截断 / 审核规则滞后 / 数据卷提示缺失 |
| 重复 | 1 类 | 两份 SQL 并存且内容不一致（25 表旧版 vs 41 表新版） |

### 4.2 错误类修复明细（6 项）

| # | 位置 | 问题 | 修复 |
|---|------|------|------|
| E-1 | 后端（02/03/05 文档声称存在） | `GET /api/health` 不存在，实际返回 `{"code":5000,"系统繁忙"}`（JwtAuthFilter 白名单预留了 /health 但无控制器） | 新增 `common/HealthController.java`，返回 `Result.success("ok")`；重建镜像后实测 `{"code":0,"message":"success","data":"ok"}` 与文档完全一致 |
| E-2 | docker-compose.md | 完全未提 `.env`，而 compose 第 55 行 `JWT_SECRET: ${JWT_SECRET:?}` 为 fail-fast，新机器直接 `up` 会报错退出 | 快速启动章节新增"第 1 步：复制 `.env.example` 为 `.env`"（含示例密钥说明 + `openssl rand -base64 32` 生成方式） |
| E-3 | mysql-deployment.md | Docker 方式写 MySQL 映射宿主机 3306，实际 compose 为 3307，与 docker-compose.md 自相矛盾 | 改为 `3307`，注明"与 docker-compose.md 保持一致" |
| E-4 | scripts 00-check-env.bat/.sh | 用未定义的 `%BACKEND_DIR%` / `$BACKEND_DIR` 判断 Maven Wrapper，无全局 Maven 的新机器被误报"未包含 Maven Wrapper" | 改用相对路径：`%~dp0..\..\backend\mvnw.cmd` / `$SCRIPT_DIR/../../backend/mvnw` |
| E-5 | 05-troubleshooting.md | 称 jar 部署日志默认在 `logs/qingqi.log`，实际 application.yml 未配置 `logging.file.name`，仅输出控制台 | 改为"默认输出控制台；如需文件日志自行配置 `logging.file.name: logs/qingqi.log`" |
| E-6 | scripts 00-check-env.bat/.sh | MySQL 连接失败仍计 PASS、Redis 缺失仍计 PASS，汇总数失真 | MySQL：连接成功才 PASS、失败计 FAIL；Redis：连通才 PASS（可选依赖，不连通不计 FAIL） |
